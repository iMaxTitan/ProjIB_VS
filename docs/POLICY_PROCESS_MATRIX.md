# Матрица "Политики / СУІБ -> Процессы -> Процедуры"

> Последнее обновление: 2026-03-31
> Источник: живая PostgreSQL БД через SSH + локальные документы `docs/BsDoc`

## Цель

Этот документ фиксирует соответствие между:

1. нормативными документами ИБ / СУІБ в KB;
2. текущими процессами в БД;
3. процедурами в БД;
4. фактическим операционным покрытием:
   - шаблоны задач;
   - реальные задачи;
   - часы выполнения.

Главная идея: для проекта верхний уровень должен задаваться не абстрактным `SOC`, а политиками и требованиями СУІБ.

## Что уже хорошо отражено в модели

### Сильное совпадение "политика -> процесс"

- Моніторинг та реагування на події та інциденти ІБ
- Управління правами доступу
- Управління ризиками інформаційної безпеки
- Управління документацією СУІБ
- Навчання та підвищення обізнаності у сфері ІБ
- Управління безпекою інформаційних систем
- Управління безпекою обчислювальних систем

### Частично отражено, но требует уточнения

- Управління безпекою мережі
- Резервне копіювання та відновлення ІС
- Життєвий цикл ІС
- Безперервність сервісу ІБ
- Вибір технологій та засобів ІБ

### Не выражено как отдельный процесс верхнего уровня

- криптографічний захист інформації
- захист від зловмисного коду
- мобільні пристрої
- фізична безпека серверних та комунікаційних приміщень

## Главные разрывы модели

### 1. KB и процессы живут параллельно

В `kb_documents` есть нужные политики, но `process_id` у документов фактически не используется как рабочая привязка.

Следствие:

- документ есть;
- процесс есть;
- но связь между ними не закреплена как источник истины.

### 2. Не все политики выражены в виде процесса

Часть политик уже лежит в KB, но не имеет явного операционного отражения в `processes`.

### 3. Есть процессы без операционного покрытия

Самый явный пример:

- `Управління безпекою мережі`:
  - `2` процедуры
  - `0` шаблонов
  - `0` задач

То есть процесс в модели есть, но как операционный контур он ещё не живёт.

### 4. Шаблоны есть, но используются слабо

По всей системе:

- `manual`: `1464`
- `template`: `136`

Шаблонная модель пока не стала основным рабочим контуром.

### 5. Слабое качество фактических задач

По ряду процессов большинство задач имеют пустой `title`, особенно:

- Моніторинг та реагування на події та інциденти ІБ
- Управління правами доступу
- Управління безпекою інформаційних систем
- Управління документацією СУІБ

Это мешает аналитике и будущему KPI.

## Что делать дальше

### Приоритет 1. Закрепить явную связь "документ KB -> процесс"

Нужно ввести рабочую матрицу соответствия в системе:

- один документ может покрывать один или несколько процессов;
- один процесс может ссылаться на один основной и несколько связанных документов.

Минимум:

- заполнить/использовать `kb_documents.process_id` там, где связь 1:1;
- для связей many-to-many позже завести отдельную таблицу.

### Приоритет 2. Привести process model к реальным политикам СУІБ

Не отталкиваться от общего слова `SOC`, а отталкиваться от:

- Політика ІБ;
- Політики СУІБ;
- конкретные `Вимоги ІБ ...`

### Приоритет 3. Дотянуть "пустые" процессы до рабочего состояния

В первую очередь:

- `Управління безпекою мережі`
- continuity / backup / recovery контур
- направления без отдельного процесса:
  - malware
  - crypto
  - mobile
  - physical security

### Приоритет 4. Переделать шаблоны задач в семантические

Для будущего KPI шаблон должен хранить не только `title/content`, но и:

- `work_mode`
- `work_type`
- `default_expected_hours`
- `effort_weight`
- `requires_comment`

## Практический вывод

Правильная верхняя модель для проекта:

```text
Политика / Требования СУІБ
  -> Процесс
    -> Процедуры
      -> Шаблоны задач
        -> Планировщик / фактическое выполнение
          -> KPI / coverage / planned-unplanned analytics
```

Текущая структура БД уже близка к этой модели, но ей не хватает:

- явной привязки процессов к документам KB;
- выражения всех ключевых политик в process model;
- перевода execution из manual flow в template-driven flow.
