# Целевая карта процессов и roadmap

> Последнее обновление: 2026-03-31
> Основание: живая БД, KB-документы СУІБ, `docs/POLICY_PROCESS_MATRIX.md`

## Целевая логика

Верхний уровень модели должен строиться так:

```text
Политика / Вимоги СУІБ
  -> Process
    -> Procedures
      -> Task templates
        -> Planner execution
          -> KPI / coverage / planned-unplanned
```

Главный принцип:

- не строить модель вокруг слова `SOC`;
- строить её вокруг услуг и направлений всего подразделения ИБ;
- процессы в БД должны быть нормализованной операционной проекцией политик СУІБ.

---

## Целевая карта процессов

Ниже 3 группы:

1. оставить как есть;
2. уточнить и расширить;
3. добавить как отдельные процессы или поднаправления.

---

## 1. Процессы, которые стоит оставить как основу

### 1. Моніторинг та реагування на події та інциденти ІБ

Основа правильная. Это ваш operational security core.

Целевые процедуры:

- Моніторинг подій ІБ
- Тріаж та первинний аналіз подій
- Управління інцидентами ІБ
- Threat hunting
- Detection engineering та tuning
- Post-incident review

Статус:

- процесс очень живой;
- процедур сейчас мало для такого веса;
- это первый кандидат на углубление.

### 2. Управління правами доступу

Основа правильная.

Целевые процедуры:

- Організація управління правами доступу
- Аудит управління правами доступу
- Періодичний review доступів
- Контроль SoD / excessive privileges
- Нормативно-методична підтримка access governance

### 3. Управління ризиками інформаційної безпеки

Основа правильная.

Целевые процедуры:

- Ідентифікація ризиків
- Оцінка ризиків
- План обробки ризиків
- Моніторинг ризиків
- Контроль виконання плану обробки
- Методична підтримка
- Continuity / resilience contour

### 4. Управління документацією СУІБ

Основа правильная.

Целевые процедуры:

- Створення документації
- Оновлення документації
- Введення в дію / публікація / відкликання
- Методичний супровід імплементації
- Контроль актуальності

### 5. Навчання та підвищення обізнаності у сфері ІБ

Основа правильная.

Целевые процедуры:

- Планування навчання
- Підготовка матеріалів
- Організація навчання
- Аналіз результатів
- Позапланове інформування
- Методичний супровід

### 6. Взаємодія з контрагентами

Основа правильная, но это скорее governance/service-delivery support.

Целевые процедуры:

- Договірне забезпечення
- Тендерна участь
- Перевірка контрагентів
- Методичний супровід бізнес-проєктів
- Експертиза архітектурних рішень

### 7. Облік та звітність

Основа правильная как support process.

Целевые процедуры:

- Звітність щодо надання послуг ІБ
- Внутрішня звітність підрозділу ІБ
- Облік ТМЦ
- Підготовка доказової / звітної бази

## 2. Процессы, которые надо уточнить и довести

### 8. Управління безпекою інформаційних систем

Сейчас это хороший umbrella-процесс, но он перегружен несколькими темами.

Нормальная цель:

- security requirements for IS
- security configuration baseline for IS
- vulnerability management for IS
- secure lifecycle / architecture review
- backup / recovery requirements

Нужно не ломать процесс сразу, а очистить его внутренние процедуры.

### 9. Управління безпекою обчислювальних систем

Оставить, но сделать понятнее как endpoint / compute hardening domain.

Целевые процедуры:

- baseline hardening
- контроль соответствия baseline
- vulnerability management for compute
- remediation tracking

### 10. Управління безпекою мережі

Процесс нужен, но сейчас фактически пустой.

Целевые процедуры:

- baseline hardening мережевого обладнання
- контроль відповідності baseline
- vulnerability management for network
- remediation tracking

Это один из самых явных operational gaps.

### 11. Управління захистом даних в інформаційних системах

Сейчас туда смешаны:

- anthropogenic factor
- removable media
- software usage control
- methodological support

Процесс полезный, но его стоит переопределить как более ясный data protection / user behavior / DLP contour.

Целевые процедуры:

- Контроль ризикових дій користувачів
- Контроль інформаційних активів і каналів витоку
- Контроль розсилок / data transfer
- Контроль змінних носіїв
- Контроль нерегламентованого ПЗ
- Методична підтримка підрозділів

## 3. Направления, которые стоит выразить явно

Эти темы уже есть в KB-политиках, но слабо выражены в process model.

### A. Криптографічний захист інформації

Вариант 1:

- отдельный процесс

Вариант 2:

- отдельный крупный подпроцесс в `Управління безпекою інформаційних систем`

Рекомендация:

- если объём работ регулярный и измеримый, делать отдельный процесс;
- если работы мало, сначала вести как отдельный policy-linked procedure cluster.

### B. Захист від зловмисного коду

Рекомендация:

- не делать сразу отдельным верхним процессом;
- сначала выразить как процедуры в двух местах:
  - monitoring/incident contour;
  - compute/endpoint security contour.

### C. Безпека мобільних пристроїв

Рекомендация:

- сначала как поднаправление в compute / IS security;
- если задач много и есть отдельная услуга, потом выносить.

### D. Фізична безпека серверних та комунікаційних приміщень

Рекомендация:

- если ИБ-подразделение реально это обслуживает регулярно, оформить отдельным process area;
- если участие эпизодическое, держать как процедуру в IS / infrastructure governance.

### E. Безперервність сервісу ІБ

Рекомендация:

- сейчас оставить в контуре risk management;
- но выделить как отдельную процедуру/набор процедур:
  - continuity planning
  - resilience testing
  - recovery readiness review

- Управління документацією СУІБ

- Взаємодія з контрагентами

### Уровень D. Candidate explicit domains

- Криптографічний захист інформації

## Рекомендованный roadmap

## Phase 1. Нормализация модели

Срок: `3-5 дней`

Цель:

- зафиксировать целевую карту процессов;
- связать процессы с документами KB;
- определить, какие policy domains являются:
  - отдельным процессом;
  - подпроцессом;
  - процедурным кластером.

Задачи:

- утвердить canonical list процессов;
- составить таблицу `policy -> process`;
- отметить ownership по каждому процессу;
- определить candidate gaps.

Результат:

- одна каноническая process map;
- больше не спорим, что у вас верхний уровень: это политики/направления СУІБ.

## Phase 2. Очистка существующих процессов

Срок: `1-2 недели`

Приоритет:

1. `Моніторинг та реагування на події та інциденти ІБ`
2. `Управління безпекою інформаційних систем`
3. `Управління правами доступу`
4. `Управління ризиками інформаційної безпеки`

Задачи:

- пересмотреть описания процессов и процедур;
- убрать размытые формулировки;
- развести governance vs execution;
- выделить недостающие operational procedures.

Результат:

- процессы становятся пригодными не только для планов, но и для KPI.

## Phase 3. Заполнить пустые operational gaps

Срок: `1 неделя`

Главные кандидаты:

- `Управління безпекою мережі`
- `backup/recovery`
- `continuity`
- policy areas без явного процесса

Задачи:

- создать или активировать процедуры;
- добавить минимальные шаблоны задач;
- обеспечить, чтобы у каждого процесса был реальный execution path.

Результат:

- исчезают процессы-"декорации", у которых 0 шаблонов и 0 задач.

## Phase 4. Переделка шаблонов задач

Срок: `1-2 недели`

Цель:

- сделать шаблоны главным инструментом execution.

Новые поля шаблона:

- `work_mode`
- `work_type`
- `default_expected_hours`
- `effort_weight`
- `requires_comment`

Задачи:

- классифицировать существующие шаблоны;
- создать недостающие шаблоны по процедурам;
- перевести planner flow на template-first.

Результат:

- меньше manual ввода;
- лучше качество данных;
- основа для нового KPI.

## Phase 5. Очистка фактических задач

Срок: `3-5 дней`

Цель:

- убрать аналитическую слепоту из-за пустых названий и ручного мусора.

Задачи:

- проанализировать пустые `daily_tasks.title`;
- ввести обязательные значения от шаблона;
- минимизировать ручной ввод свободного текста;
- оставить комментарий только для исключений / incident work.

Результат:

- данные становятся пригодными для разрезов planned/unplanned, by process, by company.

## Phase 6. Новый KPI и capacity model

Срок: `1-2 недели`

Цель:

- завязать KPI на новую process/policy model.

Основные метрики:

- capacity
- planned baseline
- reserve
- unplanned load
- incident share
- coverage
- overload gap

Результат:

- KPI перестаёт быть просто `fact / planned`.

## Практическая рекомендация

Не нужно сейчас взрывать модель и создавать десятки новых процессов.

Правильная стратегия:

1. закрепить process map от политик СУІБ;
2. довести до качества уже существующие процессы;
3. только потом выносить недостающие policy domains в отдельные процессы там, где это реально операционно нужно.

Иначе получится очередной красивый справочник без хорошего execution.
